## Problem Statement

Dos problemas de experiencia de usuario con Cookidoo que afectan el uso familiar semanal:

**Problema 1 — Discovery:** El buscador de Cookidoo tiene ranking malo, mezcla idiomas sin traducción, y es difícil encontrar recetas que encajen con los gustos de la familia. El usuario ya tiene colecciones propias con recetas aprobadas, pero ampliar esa colección con recetas nuevas es lento y frustrante.

**Problema 2 — Planning:** La planificación semanal se hace día a día, de memoria, sin criterio. El usuario quiere un plan de 5 días que use las recetas que la familia ya conoce y le gustan, balanceado por características familiares (hijos chicos), y que permita iterar rápido hasta llegar al plan final.

---

## Demand Evidence

- El usuario es el único que busca recetas en casa — hay fricción personal concreta.
- La planificación es reactiva (el mismo día, de memoria) — el costo de no planificar es tiempo y variedad reducida.
- Ya tiene colecciones propias de Cookidoo con recetas aprobadas — el problema no es falta de recetas sino falta de un sistema para usarlas bien.
- El proyecto tiene potencial de producto real: muchas familias con Thermomix enfrentan el mismo problema.

---

## Flujo actual (Status Quo)

1. Día a día, alguien propone qué cocinar (sin criterio).
2. El usuario busca en Cookidoo o en memoria de recetas conocidas.
3. Resultado: repetición de las mismas recetas, baja variedad, tiempo perdido buscando.
4. Nuevas recetas: búsqueda manual en Cookidoo (mal buscador), luego subida con `/receta` si se encuentra algo interesante.

---

## Target User

**Usuario directo:** El que cocina en casa y gestiona el Thermomix (el desarrollador, en este caso).
**Usuarios indirectos:** La familia (los que comen). El criterio de balance incluye: niños chicos, variedad nutricional, preferencias conocidas.

---

## Premises

1. **La librería de recetas ya existe en Cookidoo** — son las Custom Collections propias del usuario. No hay que construir una nueva fuente de verdad en Cookidoo.
2. **Cookidoo es el origen, el local es el caché de trabajo** — las recetas viven en Cookidoo (para tenerlas en la app), pero el planning itera sobre una DB local para ser rápido.
3. **Claude es la UI del planning interactivo** — como `/receta`, no hace falta una web app. El MCP Prompt `/semana` guía el flujo conversacional.
4. **Discovery tiene dos vías**: desde las colecciones curadas de Cookidoo (API nativa) y desde web (URL/texto → `/receta` existente → se añade a la colección).
5. **No hay API de búsqueda en el catálogo de Cookidoo** — `get_managed_collections()` da acceso a colecciones curadas, pero no hay endpoint de búsqueda por texto libre. El discovery externo depende de web search + `/receta`.
6. **El perfil familiar persiste localmente** — no en `.env` sino en un archivo estructurado local que Claude puede leer y actualizar.

---

## Arquitectura

```
Cookidoo (fuente de verdad)
  └── Custom Collections (recetas aprobadas)
  └── Calendar (historial y plan futuro)
  └── Managed Collections (para discovery)

DB Local (SQLite — rápido, offline)
  └── recipes: id, name, source_url, last_cooked, tags, family_rating
  └── weekly_plans: week_start, plan_json
  └── family_profile: ages, restrictions, preferences

MCP Tools (nuevos)
  ├── sync_library       → Cookidoo collections → DB local
  ├── plan_week          → lee DB local → propone plan
  ├── confirm_plan       → escribe plan al calendario de Cookidoo
  ├── browse_cookidoo    → managed collections → recetas candidatas
  └── rate_recipe        → actualiza family_rating en DB local

MCP Prompt
  └── /semana            → orquesta todo el flujo de planning semanal
```

## Approaches Considerados

### Approach A: Solo Planning (mínimo viable)
- 2 MCP tools: leer colecciones + escribir calendario
- Sin DB local — cada propuesta llama a la API
- Sin Discovery
- Effort: S | Risk: Bajo | Completeness: 5/10

### Approach B: Plataforma completa
- 5+ MCP tools + Discovery nativo Cookidoo + Discovery externo + perfil familiar
- Todo construido en paralelo
- Effort: L | Risk: Medio | Completeness: 9/10

### Approach C: `/semana` MCP Prompt + DB local (elegido)
- Mismo patrón que `/receta` — un prompt que guía el flujo completo
- DB local SQLite para velocidad de iteración
- Cookidoo como origen y destino final del plan
- Discovery: colecciones de Cookidoo + web → `/receta` existente
- Effort: M | Risk: Bajo-Medio | Completeness: 8/10

---

## Recommended Approach: C

### Por qué C

Encaja con el patrón establecido en el proyecto. `/receta` funciona porque Claude guía el flujo — `/semana` hace lo mismo para planning. La DB local resuelve el constraint de velocidad sin romper Cookidoo como fuente de verdad.

### Nuevos MCP Tools

**`sync_library(collection_names: list[str] | None) → dict`**
- Lee Custom Collections de Cookidoo (todas, o solo las indicadas por nombre)
- **Estructura real de la API:** `CookidooCollection` no tiene `.recipes` directamente — tiene `.chapters` (lista de `CookidooChapter`). Hay que iterar `col.chapters[].recipes` para obtener las recetas. Cada `CookidooChapterRecipe` tiene `id`, `name`, `total_time` (int, en segundos).
- Upsert por `id` (Cookidoo recipe ID como clave primaria): si existe → actualiza `synced_at` y `collection`; si no → inserta nueva fila
- Todo el upsert va dentro de una sola transacción SQLite (performance)
- **Fase 2 — historial de calendario:** llama `get_recipes_in_calendar_week(date)` para las últimas N semanas y actualiza `last_cooked` y `times_cooked`. `CookidooCalendarDay.id` es la fecha como string `"YYYY-MM-DD"`. Las recetas del catálogo aparecen en `.recipes`; las custom en `.customer_recipe_ids`.
- **Error handling (dos fases independientes):** si la fase 2 (calendario) falla, se loguea y se continúa — el sync de recetas ya fue exitoso. Retorna `{total, new, updated, calendar_synced: bool}`.

**`plan_week(week_start: str, constraints: str | None) → str`**
- Lee `recipes.db` local (sin llamada a Cookidoo API en esta fase)
- Para el historial anti-repetición: llama `get_recipes_in_calendar_week(date)` cuatro veces (semanas -1, -2, -3, -4). Esto sí hace llamadas API pero solo una vez por ejecución, no en cada iteración.
- Retorna un JSON estructurado que Claude usa para presentar el plan en el chat:
  ```json
  {
    "week_start": "2026-04-21",
    "plan": {
      "monday":    {"id": "...", "name": "Pasta Boloñesa", "rating": 4},
      "tuesday":   {"id": "...", "name": "Pollo al horno", "rating": null},
      "wednesday": {"id": "...", "name": "Lentejas", "rating": 5},
      "thursday":  {"id": "...", "name": "Arroz con verduras", "rating": 3},
      "friday":    {"id": "...", "name": "Tortilla española", "rating": 4}
    },
    "avoided": ["Merluza al vapor"],
    "notes": "Sin pescado esta semana según constraints."
  }
  ```
- `constraints`: string libre procesado por Claude en la capa de prompt, no por el tool. El tool solo filtra por `family_rating >= 3` y excluye recetas usadas en las 4 semanas anteriores.
- Priorización: recetas con `family_rating` más alto primero; recetas con `last_cooked` más antiguo tienen preferencia en empate.

**`confirm_plan(plan_json: str) → str`**
- Recibe el plan aprobado por el usuario. Schema:
  ```json
  {
    "week_start": "2026-04-21",
    "plan": {
      "monday":    "recipe_id_or_null",
      "tuesday":   "recipe_id_or_null",
      "wednesday": "recipe_id_or_null",
      "thursday":  "recipe_id_or_null",
      "friday":    "recipe_id_or_null"
    }
  }
  ```
- Días opcionales (null = sin receta ese día). No todos los días tienen que tener receta.
- **API confirmada (The Assignment 2026-04-19):** ambos endpoints aceptan fecha:
  - `add_recipes_to_calendar(day: date, recipe_ids: list[str])` → catálogo Cookidoo
  - `add_custom_recipes_to_calendar(day: date, recipe_ids: list[str])` → recetas custom
  - Ambos retornan `CookidooCalendarDay`
- El campo `source` en la DB determina qué API usar: `'cookidoo_custom'` → `add_custom_recipes_to_calendar`; `'cookidoo_managed'` o `'external'` → `add_recipes_to_calendar`.
- Días con error se reportan individualmente — un fallo no cancela los demás días.
- Retorna confirmación con los días escritos y cualquier error por día.

**`rate_recipe(recipe_id: str, rating: int, notes: str | None) → str`**
- Actualiza `family_rating` (1-5) y notas en SQLite local
- Permite que el planning futuro priorice mejor

**`browse_cookidoo_collections(page: int = 0) → list`**
- Llama `get_managed_collections()` de la API
- **Estructura real (The Assignment 2026-04-19):** cada `CookidooCollection` tiene `.chapters` (lista de `CookidooChapter`), y cada capítulo tiene `.name` y `.recipes` (lista de `CookidooChapterRecipe` con `id`, `name`, `total_time` en segundos).
- Retorna lista de colecciones con sus capítulos y recetas — Claude puede presentarlas al usuario para exploración
- Punto de entrada para el discovery nativo
- **Nota:** desbloqueado — la estructura de CookidooChapter está confirmada.

### MCP Prompt `/semana`

```python
@mcp.prompt()
def semana(semana: str = "próxima") -> list[Message]:
    """Planificar la semana con recetas de la familia."""
    # Lee ~/.thermomix/family_profile.json al momento de construir el prompt
    # y lo embebe en el contexto del sistema (igual que /receta embebe las reglas)
    # Flujo que define el prompt:
    # 1. Ofrece sync_library si synced_at > 24h o si es la primera vez
    # 2. Pregunta constraints de la semana (si el usuario quiere añadir alguna)
    # 3. Llama plan_week → presenta el plan en formato legible
    # 4. Itera: el usuario puede pedir cambios, el prompt vuelve a llamar plan_week
    #    o modifica el plan directamente en la conversación
    # 5. Al aprobarlo: llama confirm_plan con el JSON final → escribe al calendario
```

El `family_profile.json` se lee en el handler del prompt y se embebe en el mensaje del sistema. No se necesita un tool separado para leerlo — es configuración estática como las reglas de `/receta`.

### Perfil Familiar

Archivo `~/.thermomix/family_profile.json`:
```json
{
  "members": [
    {"name": "Adulto 1", "role": "adult"},
    {"name": "Niño 1", "age": 4, "role": "child"}
  ],
  "restrictions": ["sin mariscos"],
  "preferences": ["pasta", "arroz", "verduras"],
  "avoid": ["picante"],
  "servings": 4
}
```

### DB Local

`~/.thermomix/recipes.db` — SQLite:
```sql
CREATE TABLE recipes (
  id TEXT PRIMARY KEY,           -- Cookidoo recipe ID
  name TEXT NOT NULL,
  source TEXT,                   -- 'cookidoo_custom' | 'cookidoo_managed' | 'external'
  collection TEXT,               -- nombre de la colección
  last_cooked DATE,
  times_cooked INTEGER DEFAULT 0,
  family_rating INTEGER,         -- 1-5, null si no valorada
  tags TEXT,                     -- JSON array
  synced_at TIMESTAMP
);

CREATE TABLE weekly_plans (
  week_start DATE PRIMARY KEY,
  plan JSON NOT NULL,            -- {mon: recipe_id, tue: recipe_id, ...}
  created_at TIMESTAMP,
  confirmed BOOLEAN DEFAULT FALSE
);
```

## Discovery Flow (dos vías)

### Vía 1: Desde Cookidoo (DESBLOQUEADO)
`browse_cookidoo_collections()` está desbloqueado — la estructura de `CookidooChapter` está confirmada (ver Open Questions #1 resuelto). Claude puede presentar las colecciones curadas con sus capítulos y recetas para que el usuario explore. El usuario puede pedir añadir una receta a su colección propia desde la conversación.

### Vía 2: Externa (URL/texto/foto)
1. Usuario usa `/receta` existente → receta creada en Cookidoo como custom recipe
2. Después: `sync_library()` → receta entra a DB local automáticamente
3. Si `COOKIDOO_LIBRARY_COLLECTION` está definido en `.env`, `/receta` añade automáticamente la nueva receta a esa colección vía `add_recipes_to_custom_collection()`. Si no está definido, la receta queda como custom recipe sin colección y el usuario la asigna manualmente.

## Success Criteria

- `/semana` propone un plan de 5 días en menos de 30 segundos (usando DB local; sin llamadas a la API en la iteración)
- El plan no repite recetas de las últimas 2 semanas (lee historial de Cookidoo)
- El usuario puede iterar el plan ("cambia el martes por algo más rápido") en el mismo chat
- Al confirmar, el plan aparece en el calendario de Cookidoo
- Discovery desde colecciones Cookidoo añade receta a colección propia y a DB local
- Discovery externo (URL → /receta → colección) funciona end-to-end
